# Mermaid SVG scheme

What Mermaid 11.17.2 actually emits for a `stateDiagram-v2`, and which parts of it `StatechartViz` treats as a
contract. Everything here was read off a rendered document, not off Mermaid's documentation.

Observed on 2026-08-28 with Mermaid `11.17.2` — the pinned devDependency of `packages/viz` — in Chromium via
Playwright, at `securityLevel: "strict"` (the Mermaid default). To reproduce: `pnpm run dev`, open `/spike/`
(`spike/index.html`), inspect `window.__spike`; `?securityLevel=loose|sandbox` switches the level.

Three diagrams were rendered: the proposal's `trafficLight` (a compound state, `[*]` inside it, `%%` directives) and
`square` (two candidates for one event), plus a `parallel` fixture (two regions via `--`, region finals,
`state "desc" as id`, `state c1 <<choice>>`).

> [!NOTE]
> The spike page overrides styles with `!important`. The shipped component does not — it scopes its rules by SVG id
> instead, as described under [Highlighting](#highlighting). Read `spike/index.html` as evidence, not as a model.

## Render output

`mermaid.render(svgId, text)` resolves to `{ svg, bindFunctions }`. `svg` is the markup of a single element:

```html
<svg id="<svgId>" class="statediagram" width="100%" viewBox="…" role="graphics-document document">
```

Inside it: a `style` element whose every rule is scoped with `#<svgId> …`, then one `g` wrapping `g.root`, which
holds `g.clusters`, `g.edgePaths`, `g.edgeLabels` and `g.nodes`, plus two `defs` for markers and drop-shadow filters.
Every `id` in the output carries the `<svgId>-` prefix; the arrow marker is `<svgId>_stateDiagram-barbEnd`.

`svgId` values are generated by the component as `scv-1`, `scv-2`, … from a module-global counter, so two diagrams on
one page never collide.

`%% @…` directive lines produce no nodes: the node list equals the set of states in the diagram.

After rendering, the component strips the `height` attribute and clears `style.maxWidth`, then sets `width` and
`height` to `100%`, so the panel owns the size. `svg-pan-zoom` then wraps the content in `.svg-pan-zoom_viewport`.

## State nodes

```html
<g class="node  statediagram-state" id="<svgId>-state-<mermaidId>-<n>" data-look="classic" transform="…">
    <rect class="basic label-container" …/>
    <g class="label">…foreignObject → div → span.nodeLabel…</g>
</g>
```

- Lives under `g.nodes`. State nodes carry **no** `data-id` attribute.
- `<n>` is an internal counter (`state-off-4`, `state-working-5`, `state-green-8`). It is not stable across diagrams
  and must not be relied on. The Mermaid id is recovered with `^<svgId>-state-(.+)-\d+$` — a greedy group, because
  Mermaid ids of this subset never contain `-`, region ids do, and an id may end in a digit (`state-s1-3` → `s1`).
- `state "All regions finished" as finished` yields the id `finished`; the label text is the description.
- `state c1 <<choice>>` uses the same `g.node.statediagram-state` scheme, but its body is a diamond `path` nested in
  a `g` rather than a `rect`.

## Composite blocks and regions

```html
<g class="statediagram-state statediagram-cluster" id="<svgId>-state-working-5" data-id="working" data-look="classic">
    <g><rect class="outer" …/></g>
    <g class="cluster-label">…foreignObject…</g>
    <rect class="inner" …/>
</g>
```

- Lives under `g.clusters`, flat: nested clusters are siblings, not DOM descendants.
- The class is `statediagram-cluster`, so a `g.cluster` selector does not match.
- A composite carries `data-id="<mermaidId>"` and needs no regex.

Parallel regions created by `--` render as
`g.statediagram-state.statediagram-cluster.statediagram-cluster-alt` with a single `rect.divider`, and **no**
`data-id`. Their ids are `<svgId>-state-<regionId>-<n>` where the first region is `divider-id-1` and the rest are
random (`id-n2331etg9vo-2`, different on every parse). Regions therefore cannot be addressed by a stable id — which
matches the config contract, where `$0` and `$1` are not Mermaid ids either.

## Start and end pseudo-states

`[*]` renders as an ordinary node under `g.nodes`, class `node default`:

| Source | Mermaid id | DOM id | Body |
| --- | --- | --- | --- |
| `[*] --> off` at the root | `root_start` | `<svgId>-state-root_start-0` | `circle.state-start` |
| `[*] --> green` inside `state working {}` | `working_start` | `<svgId>-state-working_start-5` | `circle.state-start` |
| `red --> [*]` inside `state working {}` | `working_end` | `<svgId>-state-working_end-9` | `g.outer-path`, two paths |
| `[*]` inside a region | `<regionId>_start` / `<regionId>_end` | random from the second region on | as above |

So the config's `$final` of a compound `X` maps to the Mermaid node `X_end`, and the root `$final` to `root_end`.
Region finals have no stable node.

## Edges and edge labels

```html
<g class="edgePaths">
    <path d="…" id="<svgId>-edge1" class="edge-thickness-normal edge-pattern-solid transition"
          data-edge="true" data-et="edge" data-id="edge1" data-look="classic"
          marker-end="url(#<svgId>_stateDiagram-barbEnd)"/>
</g>
<g class="edgeLabels">
    <g class="edgeLabel" transform="…">
        <g class="label" data-id="edge1">
            <foreignObject><div><span class="edgeLabel"><p>POWER_ON [hasPower] / logStart</p></span></div></foreignObject>
        </g>
    </g>
</g>
```

- The path is `path.transition[data-id="edge<i>"]`, with DOM id `<svgId>-edge<i>`. DOM order is **not** source order
  (`edge0, edge4, edge1, …`); `data-id` is the key.
- The label is `g.edgeLabel > g.label[data-id="edge<i>"]`, keyed identically. Unlabelled edges such as `[*] --> off`
  still get a label group, with a `0×0` foreignObject.
- Neither the path nor the label carries source or target ids. Those come from the parser data below.
- Labels sit on the path midpoint, so hit-testing the middle of a path returns the label's `<p>`. A click there still
  resolves to the edge through `closest("g.edgeLabel")`.

## Diagram data from the parser

`mermaid.mermaidAPI.getDiagramFromText(text)` → `diagram.db.getData()` returns `{ nodes, edges }`.

> [!IMPORTANT]
> `mermaid.parse(text)` must be called first. On a fresh Mermaid instance `getDiagramFromText` otherwise fails with
> "No diagram type detected".

- `nodes[i]` is
  `{ id, label, parentId?, isGroup, shape: "rect" | "roundedWithTitle" | "divider" | "stateStart" | "stateEnd" | "choice", domId }`.
  `domId` (`state-off-4`) equals the DOM id without the `<svgId>-` prefix, for every id that is not random.
- `edges[i]` is `{ id: "edge<i>", start, end, label }`, where `start` and `end` are Mermaid ids — `root_start` and
  `working_end` included — and `label` is the raw label text. Since `edges[i].id` equals the DOM `data-id`, the
  DOM-edge ↔ parser-edge join is by `data-id` and independent of DOM order.
- Random region ids differ between the `getDiagramFromText` call and the `render` call, because those are separate
  parses. Everything else — state ids, edge numbering, the `_start` / `_end` nodes of named scopes — is
  deterministic for the same text.

The component guards this data on the way in: it rejects a diagram whose `type` is not `stateDiagram`, rejects a
`db` with no `getData()`, drops edges whose id does not match `^edge(\d+)$` or whose `start` or `end` is missing, and
sorts what survives by index.

## Security levels

| Level | Result |
| --- | --- |
| `strict` (default) | ids, `data-id` and classes exactly as documented here; labels through `foreignObject` |
| `loose` | not needed — `strict` covers everything the component does |
| `sandbox` | `render()` returns `<iframe src="data:text/html;base64,…">`: the SVG lives in an iframe, with no DOM access, no highlighting and no clicks. Unsupported, and the component throws |

## Highlighting

Both strategies were verified against the rendered document.

**1. Toggle a class in place — chosen.** `classList.add("active")` on `g.node` or `g.statediagram-cluster` changes
the rendered stroke immediately: the computed `stroke` went from `rgb(147,112,219)` to the override. Mermaid's own
rules are `#<svgId> .node rect {…}` and `#<svgId> .statediagram-cluster rect {…}`, specificity 1,1,1, so an override
must either be scoped with the SVG id (`#<svgId> .node.active > rect`, 1,3,1) or use `!important`. The component
takes the first route. The visible frame of a cluster is `rect.outer`, nested in a `g`; a plain state's is the direct
`rect.label-container`; a choice state has no `rect` at all, and is reached through `> g > path`.

**2. Re-render with `classDef active …` plus `class a,b active` — fallback.** It works: the class lands on `g.node`
(`node active statediagram-state`) and on the cluster (`active statediagram-state statediagram-cluster`). It costs a
full Mermaid re-layout per snapshot and destroys the pan-zoom state, so it stays a documented option only.

Cursors are part of the same generated stylesheet: pointer over states and over enabled event edges, `not-allowed`
over blocked ones, default over the rest. A refused click adds `scv-denied` for 700 ms, which runs a two-cycle
keyframe flash.

## Click handling

Event delegation on the `<svg>` with `closest()` resolves every target that matters:

| Clicked element | `closest(…)` | Key |
| --- | --- | --- |
| `path.transition` | `path.transition[data-id]` | `data-id` → edge index |
| a label `span` or `p` | `g.edgeLabel` → `g.label[data-id]` | `data-id` → edge index |
| the `rect` or label of a state | `g.node` | id regex → Mermaid id |
| the `rect.inner` or `cluster-label` of a composite | `g.statediagram-cluster` | `data-id` → Mermaid id |

The shipped resolver runs against the `data-scv-*` attributes added during indexing rather than these raw selectors,
and checks edges before states so that a label overlapping a node still resolves as an edge. The outcomes are the
same.

## What the component implements

Render once with `mermaid.render(svgId, text)`, then index the SVG once:

- `data-scv-state="<mermaidId>"` on `g.node`, via the regex under [State nodes](#state-nodes), and on
  `g.statediagram-cluster`, via the `data-id` under [Composite blocks and regions](#composite-blocks-and-regions).
- `data-scv-edge="<i>"` on `path.transition` and on `g.edgeLabel`, joined to the parser edges by `data-id` per
  [Diagram data from the parser](#diagram-data-from-the-parser).
- `data-scv-event="<event>"` on the edges whose label parses as an event trigger. This is what makes an edge
  clickable, and it is the attribute the end-to-end tests select on.

Per snapshot, toggle classes on the `[data-scv-state]` and `[data-scv-edge]` elements — strategy 1 of
[Highlighting](#highlighting). The config-to-node mapping for `$final` is the table under
[Start and end pseudo-states](#start-and-end-pseudo-states); region keys and region finals have no node and are
skipped.

Override styles come from an SVG-id-scoped sheet generated per render, and `svg-pan-zoom` is attached to the same
`<svg>`.

Those three `data-scv-*` attributes are the stable contract for a host. The functions that apply them are internal
and are not exported from the package.
